# Base Prompt Library

Generated by `python scripts/check_templates.py --write-index`; do not edit by hand.

Pick the template whose purpose and recommended use match the task type, read it, and
specialize it (fill slots, prune what does not apply, add task-specific rules). Use one
primary template per prompt; borrow individual sections from a second template for
multi-domain tasks. If nothing fits, compose from `references/sections.md`.

## software

### architecture-agent
- Purpose: Design a system or solution by evaluating viable options against requirements and constraints, then specifying the recommended design and its phases.
- Use when: New systems, major integrations, migrations, and platform decisions where the design must be decided before implementation. Use product-architect when the question is what to build rather than how.
- Variables: OBJECTIVE, CONTEXT, REQUIREMENTS, CONSTRAINTS, QUALITY_ATTRIBUTES, RESOURCES, DECISION_SCOPE
- Required tools: none

### code-reviewer
- Purpose: Review a change or a set of files for correctness, security, and maintainability, producing ranked findings with evidence.
- Use when: Pull requests, diffs, single files, or modules where the user wants problems found rather than fixed. Use security-reviewer when security is the primary concern of the whole system.
- Variables: SCOPE, CONTEXT, REVIEW_FOCUS, CONVENTIONS, RESOURCES
- Required tools: file read

### codebase-analyst
- Purpose: Understand a project deeply, with evidence, before anything is recommended or changed.
- Use when: Onboarding to an unfamiliar codebase, pre-change impact analysis, architecture reviews, technical due diligence. Read-only; pair with repository-agent when changes follow.
- Variables: OBJECTIVE, CONTEXT, FOCUS_AREAS, RESOURCES, AUDIENCE
- Required tools: file read, file search

### debugging-agent
- Purpose: Find the root cause of a defect with evidence, then apply the smallest correct fix.
- Use when: Bugs, failing tests, flaky behavior, performance regressions, and production incidents where the cause is not yet known. Use repository-agent when the fix is already understood.
- Variables: SYMPTOM, CONTEXT, REPRODUCTION, RESOURCES, CONSTRAINTS, CHECKPOINT_TRIGGERS
- Required tools: file read, file search, shell or test runner

### repository-agent
- Purpose: Inspect, modify, test, and document an existing repository safely.
- Use when: Feature work, bug fixes, refactors, and integrations in an existing codebase where Claude has file and shell access. Use debugging-agent for diagnosis-first work and codebase-analyst for read-only understanding.
- Variables: OBJECTIVE, CONTEXT, REQUIREMENTS, CONSTRAINTS, ASSUMPTIONS, RESOURCES, CHECKPOINT_TRIGGERS, TEST_COMMANDS, SUCCESS_CRITERIA
- Required tools: file read, file search, file edit, shell or test runner


## security

### authentication-reviewer
- Purpose: Review authentication, session, and token handling (including OIDC and OAuth flows) against a checklist of known weaknesses, with evidence-backed findings.
- Use when: Login, SSO, OIDC or OAuth integrations, session management, password reset, and MFA implementations. Use security-reviewer for a whole-system review.
- Variables: SCOPE, CONTEXT, AUTH_STACK, RESOURCES, EXCLUSIONS
- Required tools: file read, file search

### security-reviewer
- Purpose: Review a system for credible security weaknesses and report evidence-backed findings ranked by severity.
- Use when: Security assessments of applications, services, and configurations where Claude can read the code or configuration in scope. Use authentication-reviewer for auth-specific depth and threat-modeler for design-stage analysis.
- Variables: SCOPE, CONTEXT, RESOURCES, FOCUS_AREAS, EXCLUSIONS, CONSTRAINTS
- Required tools: file read, file search

### threat-modeler
- Purpose: Build a threat model for a system from its assets, trust boundaries, and data flows, and prioritize mitigations.
- Use when: Design reviews, new features with security implications, and periodic reassessments where the goal is to enumerate threats before or instead of testing. Use security-reviewer to examine an implementation.
- Variables: SYSTEM, CONTEXT, SCOPE, RESOURCES, METHODOLOGY
- Required tools: none


## research

### comparison-agent
- Purpose: Compare named options against weighted criteria derived from the user's needs and recommend one, with the conditions that would change the recommendation.
- Use when: Product, technology, vendor, and purchasing decisions between identifiable options. Use research-agent when the options are not yet known.
- Variables: DECISION, OPTIONS, CRITERIA, CONTEXT, CONSTRAINTS, RESOURCES
- Required tools: none

### fact-checker
- Purpose: Verify specific claims against authoritative sources and give each a verdict with evidence.
- Use when: Checking articles, reports, marketing copy, or generated text for accuracy before publication or reliance. Use research-agent when the task is to learn about a topic rather than verify claims.
- Variables: MATERIAL, CONTEXT, SOURCE_POLICY, RESOURCES
- Required tools: web search or supplied sources

### research-agent
- Purpose: Perform structured, evidence-based research that separates verified fact from inference and states confidence.
- Use when: Technical, market, and background research where the answer must be supported by sources. Use comparison-agent for a decision between named options and fact-checker for verifying specific claims.
- Variables: RESEARCH_QUESTION, PURPOSE, CONTEXT, SCOPE, RESOURCES, OUTPUT_LENGTH
- Required tools: web search or supplied sources


## documents

### document-analyst
- Purpose: Analyze supplied files accurately, separating what the sources state from what is inferred, without inventing missing information.
- Use when: Questions about one or a few supplied documents of any type (PDF, Word, text, Markdown, code, CSV). Use pdf-analyst, spreadsheet-analyst, or multi-document-analyst when their specific rules matter.
- Variables: OBJECTIVE, DOCUMENTS, QUESTIONS, CONTEXT, OUTPUT_SHAPE
- Required tools: file read or attachments

### multi-document-analyst
- Purpose: Analyze several documents together, cross-referencing them, tracking coverage, and surfacing inconsistencies with provenance for every statement.
- Use when: Comparing contracts, reconciling reports, reviewing a document set for consistency, or answering questions that span many files. Use document-analyst for one or two documents.
- Variables: OBJECTIVE, DOCUMENTS, QUESTIONS, AUTHORITY_ORDER, CONTEXT
- Required tools: file read or attachments

### pdf-analyst
- Purpose: Analyze PDF documents with page-level evidence, handling long documents, tables, figures, and scanned text carefully.
- Use when: Reports, contracts, papers, manuals, and forms supplied as PDF where page references and table accuracy matter. Use document-analyst for short or plain-text material.
- Variables: OBJECTIVE, DOCUMENTS, QUESTIONS, CONTEXT
- Required tools: PDF reading

### spreadsheet-analyst
- Purpose: Analyze spreadsheets and tabular files with cell-level evidence and shown calculations, without computing from assumed data.
- Use when: Excel, CSV, and similar files where the user wants figures extracted, checked, or analyzed. Use data-analyst for statistical work on larger datasets.
- Variables: OBJECTIVE, FILES, QUESTIONS, CONTEXT, TOOLS_AVAILABLE
- Required tools: file read; code execution recommended


## business

### campaign-brief
- Purpose: Produce a campaign brief a whole team can execute from: context, SMART objectives, audience and validated insight, core message, creative direction, channels, phased timeline and budget, deliverables with RACI, and risks with a fallback.
- Use when: One specific campaign (launch, seasonal, awareness, promotion, re-launch). Use marketing-plan for a whole period and content-calendar for the posting schedule.
- Variables: CAMPAIGN, PRODUCT, MARKET, KNOWN_INPUTS, CONTEXT_FILE, RESOURCES
- Required tools: none; file read when a context file exists
- Adapted from: https://github.com/minhnv0807/ai-business-skills (02-campaign-brief-global) (MIT)

### competitor-research
- Purpose: Map direct, indirect, and adjacent competitors, benchmark their positioning, ads, content, and pricing, and identify the market gap to attack, using only evidence the user supplied or that public tools return.
- Use when: Competitive analysis before a plan, a repositioning, or a campaign; "why do people pick them over us". Use customer-insight to understand the buyer and strategy-analyst for the decision itself.
- Variables: PRODUCT, COMPETITORS, GOAL, MARKET, RESOURCES, TOOLS_AVAILABLE
- Required tools: web search recommended
- Adapted from: https://github.com/minhnv0807/ai-business-skills (08-competitor-research-global) (MIT)

### customer-insight
- Purpose: Build evidence-based customer insight: consumer versus shopper, four funnel stages, jobs to be done, persona, journey map with moments of truth, validated insights, internal monologue from real sources, and behavioral segments with actions.
- Use when: Before positioning, content, ads, or product decisions; "who actually buys this and why". Use competitor-research for the rivals and requirements-analyst for product requirements.
- Variables: PRODUCT, AUDIENCE, GOAL, SOURCES, CONTEXT_FILE
- Required tools: none; file read for supplied sources
- Adapted from: https://github.com/minhnv0807/ai-business-skills (09-customer-insight-global) (MIT)

### marketing-plan
- Purpose: Produce a complete marketing plan for a period (situation, positioning, objectives with three KPI scenarios, channel mix, budget, timeline, risks) grounded in stated inputs rather than invented benchmarks.
- Use when: Quarterly or annual marketing plans, go-to-market roadmaps, "we have no marketing plan" requests. Use campaign-brief for one campaign and strategy-analyst for a strategic yes-or-no decision.
- Variables: PRODUCT, MARKET, PERIOD, KNOWN_INPUTS, CONTEXT_FILE, RESOURCES
- Required tools: none; file read when a context file exists
- Adapted from: https://github.com/minhnv0807/ai-business-skills (00-marketing-plan-global) (MIT)

### product-architect
- Purpose: Turn a product idea into a realistic product and implementation specification, separating MVP from later phases to prevent overbuilding.
- Use when: New products, major features, and internal tools where the user has an idea and needs a buildable specification. Use architecture-agent when the product is defined and only the technical design is open.
- Variables: PRODUCT_IDEA, CONTEXT, CONSTRAINTS, KNOWN_REQUIREMENTS, RESOURCES, DEPTH
- Required tools: none

### requirements-analyst
- Purpose: Convert raw source material (notes, interviews, tickets, emails) into structured, prioritized, testable requirements with traceability and open questions.
- Use when: Preparing a specification, backlog, or statement of work from unstructured input. Use product-architect when the product itself still needs to be designed.
- Variables: OBJECTIVE, SOURCE_MATERIAL, CONTEXT, STAKEHOLDERS, FORMAT
- Required tools: none

### strategy-analyst
- Purpose: Answer a strategic business question by evaluating options against evidence and explicit assumptions, with sensitivity to what could change the answer.
- Use when: Market entry, pricing, build-versus-buy, prioritization, and investment questions where a recommendation must survive scrutiny. Use comparison-agent for narrow choices between named products.
- Variables: STRATEGIC_QUESTION, CONTEXT, CONSTRAINTS, RESOURCES, TIME_HORIZON
- Required tools: none


## data

### data-analyst
- Purpose: Answer a question from a dataset with reproducible, validated analysis and honest caveats about data quality.
- Use when: Exploratory and confirmatory analysis of datasets (CSV, database extracts, logs) where the method must be reproducible. Use spreadsheet-analyst for figure extraction from workbooks and sql-analyst for query work.
- Variables: QUESTION, DATASET, CONTEXT, TOOLS_AVAILABLE, CONSTRAINTS, OUTPUT_SHAPE
- Required tools: file read; code execution recommended

### sql-analyst
- Purpose: Write, review, or optimize SQL against a known schema, checking correctness, performance, and safety before delivery.
- Use when: Query authoring, query review, and performance tuning where the schema is available. Use data-analyst when the work is analysis rather than the query itself.
- Variables: OBJECTIVE, DIALECT, SCHEMA, EXISTING_QUERY, CONTEXT, DATA_ACCESS, CONSTRAINTS
- Required tools: none; read-only database access recommended

### visualization-agent
- Purpose: Produce honest, readable visualizations chosen from the question and the data, with the code and data preparation needed to reproduce them.
- Use when: Charts, dashboards, and figures for reports or applications. Use data-analyst when the analysis itself is the hard part.
- Variables: OBJECTIVE, DATA, AUDIENCE, ENVIRONMENT, CONSTRAINTS, OUTPUT_SHAPE
- Required tools: code execution or a charting environment

- Use when: Paid ad copy for a product or offer. Use content-calendar for organic posting and campaign-brief for the campaign itself.
- Variables: PRODUCT, PLATFORM, AUDIENCE, OBJECTIVE, KNOWN_INPUTS, CONTEXT_FILE
- Required tools: none
- Adapted from: https://github.com/minhnv0807/ai-business-skills (05-ad-copy-global) (MIT)

### content-calendar
- Purpose: Build a weekly or monthly content calendar with funnel and pillar balance, a source-type mix, a content matrix for ideas at scale, a repurposing plan, posting windows, and an owner per slot.
- Use when: Requests such as what to post this month, editorial calendars, and social media plans. Use campaign-brief for a paid campaign timeline and ad-copy for paid copy.
- Variables: PRODUCT, CHANNELS, GOAL, TEAM_RESOURCES, PERIOD, MARKET, CONTEXT_FILE
- Required tools: none
- Adapted from: https://github.com/minhnv0807/ai-business-skills (01-content-calendar-global) (MIT)


## meta

### prompt-optimizer
- Purpose: Rewrite an existing prompt toward stated optimization goals (reliability, length, clarity, a new runtime) while preserving its intent, with a change log.
- Use when: When the user knows what they want changed about a prompt (shorter, stricter output, fewer refusals, works without tools). Use prompt-reviewer when the problems are not yet known.
- Variables: PROMPT, INTENDED_TASK, OPTIMIZATION_GOALS, CONSTRAINTS, RUNTIME_HOST
- Required tools: none

### prompt-reviewer
- Purpose: Review an existing prompt for reliability problems, score it, and return an optimized version that preserves its intent.
- Use when: Any prompt the user already has (system prompts, agent instructions, templates) that needs a reliability review. Use prompt-optimizer when the problems are known and the goal is a targeted rewrite.
- Variables: PROMPT, INTENDED_TASK, RUNTIME_HOST, KNOWN_PROBLEMS
- Required tools: none


## skill

### skill-domain-expert
- Purpose: Skeleton for a model-invoked skill that produces a professional domain deliverable (plan, brief, analysis, specification) whenever a request matches its triggers, using a context file, capped information gathering, a tabled output template, and a quality checklist.
- Use when: Marketing, product, legal, finance, operations, or engineering deliverables that recur with the same structure; teams that want consistent outputs across many requests. Follows the ai-business-skills pattern (MIT).
- Variables: SKILL_NAME, DESCRIPTION, DELIVERABLE, CONTEXT_FILE, CONTEXT_CONTENTS, QUESTIONS, PRINCIPLES, OUTPUT_TEMPLATE, QUALITY_CHECKLIST, CROSS_REFERENCES
- Required tools: file read when a context file is used

### skill-local-model
- Purpose: The derived files that let a skill run on a local model runtime - a self-contained system prompt, an Ollama Modelfile, and per-runtime load instructions.
- Use when: When the skill will run on a local or small model (Ollama, LM Studio, llama.cpp, vLLM) or the user names a model under about 30B. Combine with one skill-kind template, which supplies the canonical SKILL.md.
- Variables: SKILL_NAME, PURPOSE, RULES, OUTPUT, EXAMPLES, BASE_MODEL, TEMPERATURE, NUM_CTX
- Required tools: none
- Model tiers: small, tiny

### skill-output-style
- Purpose: Skeleton for a skill that shapes how Claude responds (structure, tone, length, format) for a specific reader or house style, either for the rest of the session or whenever a matching request arrives.
- Use when: Requests like "make Claude always answer like X" (session-scoped, user-invoked, persists until an off phrase) or "when I ask for X, format it as Y" (trigger-scoped, model-invoked by its description). Reader-specific formatting, house styles, executive briefs, teaching mode, accessibility needs.
- Variables: SKILL_NAME, DESCRIPTION, READER_OR_PURPOSE, SCOPE, FACTS, RULES, EXCEPTIONS, PRESEND_CHECKS
- Required tools: none

### skill-plugin-scaffold
- Purpose: The files that turn a skill directory into a distributable Claude Code plugin (tier 2), with optional multi-runtime adapters (tier 3).
- Use when: When the user wants to share, publish, version, or install a skill through a marketplace, or asks for "a plugin like i-have-adhd". Combine with one skill-kind template for the SKILL.md itself.
- Variables: PLUGIN_NAME, VERSION, DESCRIPTION, AUTHOR, REPO_URL, CATEGORY, KEYWORDS, WHAT_IT_DOES, USAGE, EVAL_CASE, EVAL_PROMPT, EVAL_CRITERIA
- Required tools: none

### skill-tool-wrapper
- Purpose: Skeleton for a skill that drives a CLI, script, or API safely and interprets its output, with read-only defaults, narrow tool permissions, and a verdict-style report.
- Use when: Wrapping scanners, linters, test runners, deployment or infrastructure tools, and any command whose output needs interpretation. Follows the SkillSpector skill-inspector pattern (Apache-2.0).
- Variables: SKILL_NAME, DESCRIPTION, ALLOWED_TOOLS, GOAL, TOOL, OPERATING_RULES, WORKFLOW, INTERPRETATION, VERDICTS, REPORT
- Required tools: the wrapped tool; declared in allowed-tools

### skill-workflow
- Purpose: Skeleton for a skill that runs a repeatable procedure on demand (a slash command) with inputs, checkpoints, tool rules, and a report.
- Use when: Release checklists, PR readiness checks, weekly reports, onboarding runs, data refreshes, any multi-step routine the user runs more than once. Invoked by the user with arguments.
- Variables: SKILL_NAME, DESCRIPTION, ARGUMENT_HINT, ALLOWED_TOOLS, PURPOSE, INPUTS, STEPS, TOOL_RULES, OUTPUT, FAILURES
- Required tools: depends on the workflow; declared in allowed-tools


## local

### small-model-task
- Purpose: Flat single-job prompt for a small or tiny local model, where worked examples carry the specification and the output is a literal template.
- Use when: Any task compiled for model tier small or tiny (3B-9B locals, or under 3B) - classification, extraction, a single rewrite, a template fill. Use instead of a domain template when the domain template's shape cannot survive the tier adaptation.
- Variables: OBJECTIVE, INPUT_NAME, RULES, OUTPUT_TEMPLATE, EXAMPLES
- Required tools: none
- Model tiers: small, tiny
